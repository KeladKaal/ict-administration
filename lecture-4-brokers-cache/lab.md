# Лаба 4 — Kafka для двух сервисов: подними и настрой с нуля

## Ситуация

К тебе, devops-инженеру, приходит разработчик:

> «У меня есть два сервиса — сервис пользователя и сервис сборщика. Пользователь создаёт заказы, сборщик должен их получать и обрабатывать. Мне нужна между ними Kafka. Подними и настрой, пожалуйста».

Сервисы уже написаны — они в папке [`lab/`](lab/). Твоя задача — **с нуля поднять и настроить Kafka**, подключить к ней оба сервиса и проверить, что всё работает в разных ситуациях.

## Что дано — два сервиса

В `lab/` лежат два готовых сервиса, каждый со своим Dockerfile (писать их не надо):

- **user-service** — «сервис пользователя». HTTP на порту 8001, кнопка «Создать заказ» кладёт событие в топик Kafka; показывает партицию и offset.
- **picker-service** — «сервис сборщика». HTTP на порту 8002, читает топик группой потребителей и «собирает» заказы.

Оба настраиваются через переменные окружения — им всё равно, где твоя Kafka:

| Переменная | Смысл | По умолчанию |
|---|---|---|
| `KAFKA_BOOTSTRAP` | адрес брокера Kafka | `kafka:9092` |
| `TOPIC` | топик заказов | `orders` |
| `GROUP` | группа потребителей (только picker) | `pickers` |
| `NAME` | имя экземпляра сборщика (только picker) | `picker-1` |

## Часть 1 — Подними Kafka и запусти сервисы

- **Подними Kafka с нуля** — способ на твой выбор (Docker или Kubernetes). ZooKeeper не нужен, используй режим **KRaft**.
- **Собери образы** обоих сервисов из их Dockerfile.
- **Запусти сервисы** так, чтобы они видели твою Kafka (адрес через `KAFKA_BOOTSTRAP`) и были доступны на http://localhost:8001 и http://localhost:8002.
- Открой обе страницы, понажимай «Создать заказ» и убедись, что заказы доходят до сборщика.

> CLI-инструменты Kafka (`kafka-topics.sh`, `kafka-consumer-groups.sh` и др.) удобно запускать внутри контейнера брокера через `docker exec`. Путь к ним зависит от образа (например, у `apache/kafka` это `/opt/kafka/bin/`).

## Часть 2 — Ситуации через CLI

Эти проверки сделай **сам, из командной строки**. По каждой в README опиши, что сделал, что увидел и почему — связывая с понятиями лекции.

1. **Партиции и порядок.** Сделай у топика `orders` 3 партиции (`kafka-topics.sh --alter --partitions 3`, а если топика нет — `--create`). Создай новые заказы и посмотри распределение по партициям (`kafka-get-offsets.sh --topic orders`). Убедись: события одного заказа (ключ order_id) всегда идут в одну партицию.
   ⚠️ Нюанс: продюсер кэширует метаданные — после изменения числа партиций перезапусти сервис пользователя, иначе он продолжит слать в старую.
2. **Consumer group — параллелизм.** Запусти второй экземпляр сборщика в той же группе (второй контейнер с `NAME=picker-2`). Посмотри, как партиции поделились между двумя сборщиками. Что будет, если сборщиков станет больше, чем партиций?
3. **Consumer lag.** Останови сборщик, создай побольше заказов, запусти снова — убедись, что ничего не потеряно. Посмотри отставание: `kafka-consumer-groups.sh --describe --group pickers`.

## Часть 3 — Подними Kafka UI

Теперь добавь к своей Kafka веб-интерфейс — **Kafka UI** (например, образ `provectuslabs/kafka-ui` или его форк `kafbat/kafka-ui`).

- Запусти контейнер Kafka UI и подключи его к своей Kafka: адрес брокера задаётся переменной `KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS` (плюс `KAFKA_CLUSTERS_0_NAME` — любое имя кластера).
- Открой UI на http://localhost:8080 и найди свой топик `orders`, его партиции и группу `pickers`.

## Часть 4 — Ситуации через Kafka UI

Эти проверки сделай **через Kafka UI**, без командной строки:

4. **Осмотр глазами.** Найди топик `orders`: посмотри его партиции, полистай сообщения (увидишь ключ order_id и значение), открой группу `pickers` и посмотри её lag по партициям — то же, что раньше видел в CLI, но наглядно.
5. **Перечитывание (replay).** Через UI сбрось offset'ы группы `pickers` в начало (reset offsets). Посмотри, как сборщик перечитывает всю историю заказов заново. Объясни, почему в Kafka так можно, а в обычной очереди — нет.
6. **Retention.** Через UI поменяй настройку хранения топика (retention) на маленькое значение и посмотри, что старые сообщения удаляются, хотя их уже прочитали.

## Часть 5 — Мониторинг (обязательно)

Настрой мониторинг Kafka и выдели **3 ключевых графика (метрики)**, по которым в реальности стоило бы построить алерты. Для Kafka главный кандидат — **consumer lag** группы `pickers`; ещё разумны: скорость сообщений in/out, свободное место на диске брокера. Выбери **три**, построй графики и в README объясни, **почему по каждому нужен алерт**.

Инструмент — на твой выбор (например, kafka-exporter + Prometheus + Grafana).
