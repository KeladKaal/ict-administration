# Лекция 4 — Поиск и логирование (Elasticsearch)

Elasticsearch — распределённый поисковый и аналитический движок на базе библиотеки Apache Lucene. В инфраструктуре он закрывает две задачи: полнотекстовый поиск в продуктах и централизованный сбор и анализ логов. README — самостоятельный конспект: материал изложен так, чтобы разобраться без лекции. Структура: назначение и область применения → терминология → статусы и эксплуатация.

---

## Часть 1 — Назначение и область применения

### Ограничения реляционной БД

Реляционные СУБД плохо подходят для двух классов задач:

1. **Полнотекстовый поиск.** Оператор `LIKE '%...%'` не использует индексы эффективно, не учитывает морфологию, опечатки и релевантность; на больших объёмах выполняется за линейное время.
2. **Аналитика на больших объёмах.** Агрегации (подсчёты, перцентили, топ-N) по миллионам строк требуют полного сканирования и выполняются медленно.

Прикладные сценарии, где это критично:

- поиск по каталогу: миллионы товаров, запросы с опечатками, ранжирование по релевантности;
- разбор инцидента по логам: поиск по полю `trace_id` и временно́му диапазону среди логов десятков сервисов;
- оперативная аналитика: число ошибок 5xx по сервисам за период, наиболее медленные эндпоинты.

### Как Elasticsearch решает эти задачи

- **Обратный (инвертированный) индекс.** Для каждого терма хранится список документов, в которых он встречается. Поиск по тексту выполняется по индексу, а не сканированием.
- **Анализаторы.** При индексации текст разбивается на термы и нормализуется (приведение регистра, стемминг). Это обеспечивает поиск по форме слова и устойчивость к опечаткам (fuzzy search).
- **Ранжирование по релевантности.** Результаты упорядочиваются по степени соответствия запросу (алгоритм BM25).
- **Движок агрегаций.** Подсчёты, перцентили, топ-N выполняются в режиме near real-time; на их основе строятся дашборды в Kibana.

Базовый принцип: основная работа выполняется при индексации (записи), что обеспечивает высокую скорость запросов (чтения).

### Определение

> **Elasticsearch** — распределённый поисковый и аналитический движок на базе Apache Lucene, обеспечивающий полнотекстовый поиск и агрегации по большим объёмам данных в режиме near real-time.

### Стек ELK

В задачах логирования Elasticsearch применяется в составе стека ELK:

> **ELK = Elasticsearch + Logstash + Kibana**; дополняется агентами **Beats**.

Конвейер обработки: **сервисы → Filebeat / Logstash (сбор и обработка) → Elasticsearch (хранение и индексация) → Kibana (поиск и визуализация)**.

- **Elasticsearch** — хранение и поиск.
- **Logstash** — сбор и обработка данных (парсинг, фильтрация, обогащение). **Beats** (в частности Filebeat) — лёгкие агенты на хостах, отправляющие данные.
- **Kibana** — веб-интерфейс поиска и построения дашбордов.

Развёртывание централизованного логирования означает развёртывание всего конвейера. Это основной сценарий применения Elasticsearch со стороны DevOps.

### Elasticsearch и реляционная БД: разграничение

Elasticsearch не является заменой основной БД и не используется как источник истины. Существенные отличия:

- отсутствуют многодокументные транзакции (ACID);
- отсутствуют соединения (`JOIN`); модель данных денормализованная;
- модель видимости — near real-time: документ становится доступен для поиска не мгновенно (интервал обновления по умолчанию ≈ 1 с);
- данные индексируются из основной БД; при потере индекса они восстанавливаются повторной индексацией.

| | Реляционная БД | Elasticsearch |
|---|---|---|
| Назначение | Хранение данных, транзакции | Поиск и аналитика |
| Роль в системе | Источник истины | Производное хранилище |
| Транзакции (ACID) | Есть | Нет (атомарность только на уровне одного документа) |
| Соединения (JOIN) | Есть | Нет (денормализованная модель) |
| Видимость записи | Сразу после коммита | Near real-time (≈ 1 с) |
| Потеря данных | Невосстановима | Восстановима переиндексацией из БД |

В промышленной системе БД и Elasticsearch применяются совместно: БД — система записи (source of truth), Elasticsearch — производное хранилище для поиска и аналитики.

### OpenSearch

OpenSearch — открытый форк Elasticsearch и Kibana, созданный AWS в 2021 году. Причина: в 2021 году Elastic сменила лицензию Elasticsearch и Kibana с Apache 2.0 на SSPL / Elastic License, которые формально не относятся к OSI-open-source (изменение было направлено в первую очередь против облачных провайдеров). AWS взял последнюю версию на Apache 2.0 и форкнул её; компоненты переименованы: Elasticsearch → OpenSearch, Kibana → OpenSearch Dashboards. Проект остаётся на Apache 2.0 и развивается под OpenSearch Software Foundation (Linux Foundation).

Для задач поиска и логирования OpenSearch и Elasticsearch функционально близки; выбор обычно определяется лицензией и облачной платформой (AWS OpenSearch Service против Elastic Cloud), а не возможностями. Со временем их API постепенно расходятся.

## Часть 2 — Терминология: индексы, шарды, реплики

**Документ** — единица хранения, JSON-объект.
- 🛒 товар: `{"name": "Кроссовки Adidas", "price": 7990, "size": 42}`
- 📋 запись лога: `{"timestamp": "2026-06-30T03:14:00Z", "level": "ERROR", "service": "checkout", "trace_id": "abc123"}`

**Индекс** — именованная коллекция документов со схожей структурой; функционально аналогичен таблице.
- 🛒 индекс `products` — все товары
- 📋 индекс `logs-2026.06.30` — логи за день

**Маппинг (mapping)** — схема индекса: перечень полей и их типов. Определяет способ индексации и поиска; тип уже заданного поля нельзя изменить без переиндексации.
- 🛒 `price` — число, `name` — текст (анализируемый), `size` — число
- 📋 `timestamp` — дата, `level` — keyword, `message` — текст

**Шард (shard)** — самостоятельная часть индекса, которая хранит подмножество его документов и может находиться на отдельном узле. Индекс целиком может не поместиться на один сервер, поэтому его делят на шарды. Каждый шард — это полноценный мини-индекс: по нему можно искать сам по себе, а Elasticsearch объединяет результаты со всех шардов (под капотом шард — отдельный индекс Lucene). Деление на шарды обеспечивает горизонтальное масштабирование.
- 🛒 индекс из 50 млн товаров разбит на 5 шардов по разным узлам
- 📋 индекс логов за день слишком велик для одного узла → делится на шарды

**Реплика (replica)** —  Нужна для двух вещей: **отказоустойчивость** (упал узел с первичным шардом — реплика становится первичной, данные не потеряны) и **скорость чтения** (поиск можно обслуживать и с реплик, поэтому больше реплик = больше параллельного чтения). Запись идёт сначала в первичный шард, затем копируется в реплики. По умолчанию — одна реплика на шард, и она никогда не размещается на том же узле, что и её первичный шард (иначе в ней нет смысла).
- 🛒 копия шарда с товарами на другом узле — поиск по каталогу переживёт отказ узла
- 📋 копия шарда логов — логи остаются доступны, если узел упал

**Узел (node)** — экземпляр Elasticsearch. **Кластер (cluster)** — совокупность узлов. Распределение шардов выполняется автоматически; реплика не размещается на том же узле, что и её первичный шард.
- 🛒 + 📋 кластер из 3 узлов одновременно держит индекс `products` и индексы логов, распределяя их шарды по узлам

Итог: шарды отвечают за масштабирование, реплики — за отказоустойчивость и пропускную способность чтения.

## Часть 3 — Статусы и эксплуатация

### Состояние кластера

- **green** — все первичные шарды и реплики размещены;
- **yellow** — все первичные шарды размещены, часть реплик не размещена; данные доступны, отказоустойчивость снижена;
- **red** — не размещён хотя бы один первичный шард; часть данных недоступна.

Примеры: 🔴 red на индексе `products` — часть каталога не находится, пользователи видят неполную выдачу; 🟡 yellow на индексе `logs-2026.07.02` — данные логов целы, но реплики не разложились.

### Типовые проблемы

- **Unassigned shards** — шарды не размещены. Причины: отказ узла, нехватка дискового пространства, отсутствие подходящего узла для реплики. Частая причина статусов yellow и red.
- **Заполнение диска.** При достижении порогов (disk watermark) кластер ограничивает размещение шардов; при flood-stage (по умолчанию 95%) индексы переводятся в режим read-only, запись прекращается. Наиболее частая эксплуатационная авария. 📋 Чаще всего диск забивают именно логи — и тогда в read-only уходят *все* индексы, включая 🛒 `products`, то есть встаёт и запись товаров.
- **Oversharding** — избыточное число мелких шардов увеличивает накладные расходы и потребление памяти. 📋 Классический источник — логи: индекс на каждый день × год × несколько шардов складывается в тысячи мелких шардов. 🛒 Реже — отдельный индекс на каждую мелкую подкатегорию товаров.
- **JVM heap.** Тяжёлые агрегации увеличивают потребление heap вплоть до OutOfMemory. Рекомендации: размер heap ≤ 50% ОЗУ и не более ≈ 32 ГБ. Примеры тяжёлых запросов: 🛒 фасетная агрегация по всему каталогу, 📋 «топ ошибок по всем сервисам за месяц».

### ILM (Index Lifecycle Management)

**Проблема.** Логи копятся бесконечно. Обычно под них заводят по индексу на период (например, `logs-2026.07.07` — на каждый день). Без присмотра быстро набегают тысячи индексов и переполненный диск.

**Что делает ILM.** Это политика, которая **автоматически проводит индекс через стадии жизни по мере старения** и в конце удаляет его. Четыре фазы:

- **Hot** — индекс активно пишется и часто читается (свежие логи). Держат на быстром железе.
- **Warm** — запись прекращена, но данные ещё запрашивают. Индекс переводят в read-only и переносят на менее мощные узлы, чтобы освободить ресурсы.
- **Cold** — читают редко, хранят «на всякий случай». Переносят на самое дешёвое хранилище.
- **Delete** — по истечении срока хранения индекс удаляется.

Переходы между фазами задаются условиями — по возрасту индекса, его размеру или числу документов. Пример типичной политики для логов: **hot сегодня → warm через 7 дней → delete через 30 дней**.

Рядом идёт понятие **rollover**: вместо одного бесконечно растущего индекса ILM создаёт новый, когда текущий достигает порога (например, 50 ГБ или 1 день), и запись продолжается уже в новый. Так индексы остаются управляемого размера.

Итог: 📋 для логов ILM практически обязателен — без него диск переполнится (см. read-only выше). 🛒 Товары по времени не устаревают, поэтому каталог обычно не ротируют, и ILM для него не нужен.

### Резервное копирование

Реплики не заменяют резервные копии: они не защищают от ошибочного удаления данных. Применяется механизм snapshot / restore, как правило, в объектное хранилище (S3). Резервируют оба вида данных: 🛒 snapshot индекса `products`, 📋 snapshot индексов логов.

### Мониторинг

Ключевые показатели: состояние кластера, свободное место на диске, использование JVM heap, число unassigned shards.

### Разграничение ролей

- **Разработчик** — формирует запросы, анализирует логи, строит дашборды в Kibana.
- **DevOps** — развёртывание и сопровождение кластера, мониторинг, резервное копирование, управление доступом, настройка ротации (ILM).

## Краткие тезисы

- Elasticsearch — распределённый движок поиска и аналитики на базе Lucene; не замена БД, а производное хранилище.
- Два класса задач: полнотекстовый поиск и агрегации по большим объёмам.
- Логирование реализуется стеком ELK (+ Beats).
- Структура данных: документ → индекс (маппинг) → шарды (масштабирование) + реплики (отказоустойчивость) → кластер.
- Эксплуатация: контроль состояния кластера и диска; flood-stage переводит индексы в read-only; ротация — через ILM; резервные копии — snapshot/restore.
